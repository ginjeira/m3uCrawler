## 3. D4-OPEN-04 — `ReviewItem.State`

### Decisão ratificada

`catalogChangedAtUtc` inclui `ReviewItemEntity.UpdatedAtUtc` apenas quando `State == Resolved`. Consequências:

- `State == Ignored` **não** faz avançar o cursor.
- `State == Excluded` (se aplicável) **não** faz avançar o cursor.
- `State == Resolved` contribui para o cursor.

### Evidência

- `PublicationStatusService.cs:151-156`:
  ```csharp
  var resolvedReviews = await db.ReviewItems
      .AsNoTracking()
      .Where(r => r.State == ReviewItemState.Resolved)
      .Select(r => (DateTime?)r.UpdatedAtUtc)
      .MaxAsync(cancellationToken)
      .ConfigureAwait(false);
  ```
- O filtro `r.State == ReviewItemState.Resolved` é **explícito** no código.
- A invariante `Ignored ⇒ CatalogueChanged: false` está documentada em `CatalogResolver.cs:1808-1810` (citada no XML doc de `PublicationStatusService.cs:95`).

### DL-130 referência

A nova sub-decisão **`D5.1`** em `31-DECISION-LOCK.md` formaliza este filtro como parte da lista final das entidades que contribuem para `catalogChangedAtUtc`.

## 4. D4-OPEN-06 — `IsEnabled` ⇒ bump `UpdatedAtUtc`

### Decisão ratificada

As 7 entidades que contribuem para `catalogChangedAtUtc` (`CanonicalChannel`, `ChannelSource`, `Source`, `ChannelAlias`, `ExternalIdentity`, `ProviderAccount`, `ReviewItem`) bumpam `UpdatedAtUtc` (entidades com esse campo) ou `CreatedAtUtc` (alias) consistentemente em todas as mutações relevantes de `IsEnabled`.

### Evidência

Auditados 24 paths em `CatalogResolver.cs` (linhas 1666, 2232, 2272, 2354, 2696, 2716, 2771, 3179, 3213, 3262, 3317, 3350, 3364, 3419, 3514, 4121, 4132, 4171, 4183, 4235, 4245, 4509, 4521, 4538). Padrões verificados:

- **Mutação de entidade existente** (ex.: `CatalogResolver.cs:2272-2273`):
  ```csharp
  channel.IsEnabled = isEnabled;
  channel.UpdatedAtUtc = DateTime.UtcNow;
  await context.SaveChangesAsync(cancellationToken);
  ```
- **Inserção de entidade nova** (ex.: `CatalogResolver.cs:1666-1668`):
  ```csharp
  IsEnabled = true,
  CreatedAtUtc = createdNow,
  UpdatedAtUtc = createdNow,
  ```

Ambos os padrões contribuem para o cursor (`UpdatedAtUtc` em mutação; `CreatedAtUtc` e `UpdatedAtUtc` ambos = now em insert, garantindo que `MAX(UpdatedAtUtc)` vê o timestamp).

### DL-130 referência

A nova sub-decisão **`D5.2`** em `31-DECISION-LOCK.md` regista a convenção observada.

## 5. D4-OPEN-07 — `ChannelSourceObservation` excluído

### Decisão ratificada

`ChannelSourceObservationEntity` não participa no cálculo de `catalogChangedAtUtc`. A exclusão é **estrutural**, não editorial: a entidade é append-only e apenas expõe `ObservedAtUtc` (não `UpdatedAtUtc`), logo **não pode** ser seleccionada pela consulta `ComputeCatalogChangedAtAsync`.

### Evidência

- `CatalogEntities.cs:1278-1290`:
  ```csharp
  public sealed class ChannelSourceObservationEntity
  {
      public long Id { get; set; }
      public long ChannelSourceId { get; set; }
      public StreamQuality Quality { get; set; }
      public EpgState Epg { get; set; }
      public AvailabilityState Availability { get; set; }
      public long ResponseTimeMs { get; set; }
      public DateTime ObservedAtUtc { get; set; }
  }
  ```
  Não existe `UpdatedAtUtc` na entidade.
- `PublicationStatusService.cs:115-156` — a lista de 7 queries `AsNoTracking().MaxAsync(...)` cobre apenas `CanonicalChannels`, `ChannelSources`, `Sources`, `ChannelAliases`, `ExternalIdentities`, `ProviderAccounts`, `ReviewItems` (filtrado por State == Resolved). **Não há query sobre `ChannelSourceObservations`**.

### Distinção canónica mantida

A nova sub-decisão **D5.1** explicita a separação entre **estado canónico** (entidades com `UpdatedAtUtc` que afectam a próxima publicação) e **observabilidade/diagnóstico** (`ObservedAtUtc` é timestamp de medição, não sinal de mudança estrutural).

### Não-afirmação deliberada

A nova D5.1 **não** declara uma regra geral "todas as entidades sem `UpdatedAtUtc` ficam automaticamente excluídas de futuros cursores". Apenas regista a exclusão específica de `ChannelSourceObservation` no contexto do cursor actual. Ondas futuras que exijam regras mais amplas devem justificá-las explicitamente (e, se necessário, rever D5.1).
